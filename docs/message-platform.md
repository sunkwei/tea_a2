## 1. 这句话拆成三段验收

用户的要求可以拆成三件必须**先后成立**的事，每一件都要能当场看到：

| 段 | 要看到什么 | 对应需求 |
|---|---|---|
| **一、平台** | 一个进程起来，有发布接口、有订阅接口、有健康接口；重启后还在 | FR-01 ~ FR-06 |
| **二、发布订阅流程** | A 发一条，B（可能多个）收到；断线重连不丢不重（窗口内） | FR-02 ~ FR-04 |
| **三、router / watchdog 基于它跑** | router 说的话出现在平台上；watchdog 的告警与心跳出现在平台上；杀掉任一方能被发现 | FR-07 ~ FR-10 |

**这一轮的成功判据（一句话）**：跑一条命令，平台、桥接、router、watchdog 都起来；
再发一条测试消息，人能在订阅端看到「router 说的一句话」和「watchdog 的心跳/告警」，
并且把 router 杀掉之后，watchdog 在 N 分钟内报出 `router_missing`。

## 2. 决策记录

### 2.1 已定（用户 2026-11-27）

1. **自建一个消息平台**（不沿用「每个组件各自直连队列 SSE」的现状）；
2. 平台要能**跑通发布/订阅**；
3. **router 与 watchdog 基于这个平台运行**（它们的输入与输出都走平台）。

### 2.2 未定（第 10 章）

- 协议：**HTTP 还是 MQTT**（用户说「http 或 mqtt」，两者皆可，需要选一个）；
- 平台与现有队列事件流是**并存**还是**替换**；
- 桥接（队列事件 → 平台）由谁做；
- topic 命名、认证、保留窗口、多机范围、代码落点。

### 2.3 这一决定回答了前两篇草案里的哪几条

| 前一篇的问题 | 现在的答案 |
|---|---|
| 信息传播中心 Q1「信息中心是哪个源」 | **候选答案：就是这个平台**（消息板）。待 Q7 确认后那篇的 Q1 即可落定 |
| 观察者架构 Q2「结构层：router/watchdog 住哪」 | router/watchdog 仍是 Python 独立进程，但**改由平台驱动**（不再只依赖队列 SSE） |

## 3. 现状事实：两条路线各有什么（不是判断，是代码事实）

| 维度 | **HTTP（自建，Python 标准库）** | **MQTT（复用 a2_broker）** |
|---|---|---|
| 现成的东西 | 队列 `GET /api/events`：SSE 广播，**内存、无 `since`、断线即丢**；`POST /api/events`：只有本机操作员能塞 | `src/mqtt_server.cpp`：TLS、`mqtt_accounts` 账号表（device/operator）、QoS1、retained、通配符 `+`/`#`；`sched/mqtt_cli.py` 有纯标准库客户端（connect/subscribe/publish/wait_publish/keepalive） |
| 新开 topic 族要不要改 C++ | 不要（平台自己定命名） | **要**：`topic_allowed()` / `publish_allowed()` 现在只认 `mt_register/#` 与 `mt_control/...`；operator 只能发 `mt_control/+/cmd` |
| 在本机（Windows）跑 | 直接跑（标准库，无依赖） | broker **只走 TLS**（`--mqtt` 与 `--no-tls` 互斥），要先有证书；broker 与隧道信令共用一个端口 |
| 投递语义 | 自己做（至少一次 + key 去重） | QoS1（**不支持 QoS2**）；retained 在内存里，**broker 重启就丢** |
| 断线回溯 | 自己做（`since` + 窗口） | 没有（retained 只留最后一条） |
| 多机 | 要自己解决 TLS / 认证 / 公网可达 | 天然（broker 在公网那台） |
| 认证 | 自己做（本机 token） | `mqtt_accounts` + zone（已有） |
| 改动面 | 新增 1 个 Python 服务 + router/watchdog 各加一个订阅 | 新增 1 个 topic 族（C++）+ Python 客户端 + router/watchdog 订阅 |

**建议（待 Q1 确认）**：先用 **HTTP** 跑通（零 C++ 改动、本机今天就能跑），但接口语义**与 MQTT 同形**
（`topic` + `filter`（`+`/`#`）+ `payload` + `key` + `retain` + `since`），以后换 MQTT 只换传输层。
理由：用户要的是「跑起来」与「router/watchdog 接上去」，这两件事不该被 ACL、证书、C++ 编译挡住。

## 4. 术语

| 词 | 意思 |
|---|---|
| **平台 / 总线** | 本文要建的东西：发布 + 订阅 + 健康。 |
| **topic / filter** | 消息的地址；filter 支持 `+`（一层）与 `#`（其余所有层），与 MQTT 同形。 |
| **发布 / 订阅** | 前者写一条消息，后者按 filter 收。 |
| **key（幂等键）** | 同一个 key 是同一件事：重复发布只投递一次。 |
| **since** | 订阅起点（最后收到的消息 id）；用于断线重连。 |
| **窗口** | 平台保留的最近 N 条 / T 分钟，超出即过期。 |
| **retain** | 该 topic 只保留最后一条（状态类消息用，例如 `a2/heartbeat/router`）。 |

## 5. 范围

### 5.1 这次要做

1. 平台进程：发布 / 订阅 / 健康 / 单实例 / 认证 / 窗口 / 心跳（FR-01 ~ FR-06）；
2. 队列事件 → 平台的桥接（FR-07，谁做见 Q3）；
3. router 接入：订阅 + 说话发布 + 心跳（FR-08）；
4. watchdog 接入：订阅心跳 + 告警发布 + 去重（FR-09）；
5. 一条命令的端到端演练（FR-10）；
6. 回退开关：平台关掉时行为与现在一致（FR-11）。

### 5.2 这次明确不做

- **平台不做业务**：不判读、不派任务、不存任务状态。队列仍是任务的**事实源**，平台只负责分发；
- 不改队列的执行语义与既有接口（只加不改；桥接是新增进程或新增发布点，不在队列里造第二套事件）；
- 不改 agent 内核；不把 router/watchdog 搬进 C++（观察者架构 Q2 已建议维持 Python 侧）；
- 不做多租户、不做计费、不做消息加密（平台默认只听 127.0.0.1；多机见 Q8）；
- 不做图形界面（观察用订阅端 + 流水文件 + 一条命令）；
- 不做「信息中心」的业务规则（那是 `propagation-center.md` 的事；平台只是它的传输层）。

### 5.3 与另两篇的关系

```
  发布者：队列事件桥接 / 传播中心 / 外部脚本
        │  publish(topic, payload, key)
        ▼
   ┌──────────── 消息平台（本文）────────────┐
   │  topics + 窗口 + retain + /health       │
   └───────┬───────────────────┬─────────────┘
           │ subscribe         │ subscribe
           ▼                   ▼
        Router              Watchdog
   （说话 → a2/router/speech）（告警 → a2/watchdog/alert）
```

- 本文 = **传输层**；
- `propagation-center.md` = **入口层的业务**（取消息→判读→派任务→发布），它把本平台当「信息中心」；
- `observer-architecture.md` = **观察者闭环的能力清单**（心跳、自检、摘要、打扰档位），
  它的 FR-02/FR-03 正是本文 FR-08/FR-09 的落地形态。

## 7. 功能需求与验收标准

> 验收标准：「输入 → 动作 → 期望结果」，并指明在哪验。
> 「计划用例」= 实现阶段新增的测试文件（文件名占位）。

### FR-01 平台进程与配置

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-01.1 | 一条命令起平台（`--host 127.0.0.1 --port 8299 --data-dir <tea home>/bus`）；`GET /health` 返回 `{ok, version, uptime_s, subscribers, last_message_at, backlog}` | 计划用例 `tests/smoke_bus.py` |
| AC-01.2 | 端口已被占用 → **拒绝启动**并指名占用者（沿用 `smoke_port_guard` 的规矩，不静默抢端口） | 同上 |
| AC-01.3 | 同一数据目录起第二个实例 → 拒绝，并说明是谁占着（pid / 启动时间） | 同上 |
| AC-01.4 | 配置只在 tea home 一份（端口、token、窗口、上限），代码里没有硬编码的地址 | 同上 |

### FR-02 发布

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-02.1 | `POST /api/publish {"topic": "a2/test/hello", "payload": {...}}` → 200 `{id, topic, at}`；订阅者收到同一条 | 计划用例 |
| AC-02.2 | 同一个 `key` 发两次 → **只投递一次**，第二次返回**同一个 id**（幂等） | 同上 |
| AC-02.3 | topic 不符合命名规则（含空格、大写、以 `/` 开头等）→ **400**；payload 超过上限（默认 64 KB）→ **413**，都不是静默截断 | 同上 |
| AC-02.4 | `retain=true` → 之后连上的订阅者**立刻**收到该 topic 的最后一条（状态类消息用） | 同上 |

### FR-03 订阅

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-03.1 | 订阅 `filter=a2/#`，依次发 3 条 → 按发布顺序收到 3 条，id 递增 | 计划用例 |
| AC-03.2 | 断开、带 `since=<最后 id>` 重连 → 收到窗口内漏掉的，且**没有一条重复**（按 id 去重） | 同上 |
| AC-03.3 | `since` 早于窗口起点 → 明确告知「更早的已过期，从 `<最早 id>` 开始」，不是静默少给 | 同上 |
| AC-03.4 | 订阅者消费很慢（不读流）→ 有上限（条数/字节），超出按策略处理（断开 / 丢最旧）并**计数**，`/health` 能看到 | 同上 |
| AC-03.5 | 订阅端进程被杀 → 平台在 N 秒内发现并把它从订阅者列表里摘掉（`/health` 的数字对得上） | 同上 |

### FR-04 窗口与保留

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-04.1 | 窗口可配（默认建议 **1000 条 / 60 分钟**，以先到者为准）；超出的消息不可再取 | 计划用例 |
| AC-04.2 | 重启后窗口内消息是否还在，按 Q6 的决定验收（要么落盘还在，要么文档写明「只留内存」） | 同上 |
| AC-04.3 | `retain` 的 topic 在重启后是否还在，同样按 Q6 决定 | 同上 |

### FR-05 认证

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-05.1 | 默认只监听 `127.0.0.1`；发布/订阅必须带 token（token 在 tea home 的文件里，**0600**） | 计划用例 |
| AC-05.2 | 不带 token / token 错 → **401**；`GET /health` 免鉴权（只读，不含敏感内容） | 同上 |
| AC-05.3 | 把监听地址改成 `0.0.0.0` 时启动日志必须**明确警告**（这条线不该随手越） | 同上 |

### FR-06 平台健康

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-06.1 | 平台写心跳文件（时间戳 + pid）；`/health` 列出订阅者（身份、连接时间、最后收到消息时间） | 计划用例 |
| AC-06.2 | 平台被杀 → 自检命令报「平台不在」；router/watchdog 日志写「平台不可达，N 秒后重连」，**不崩** | 同上 |

### FR-07 桥接：队列事件 → 平台

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-07.1 | 队列里创建一个任务 → 平台出现 `a2/queue/task` 消息（含 `task_id`、`type`、时间、工作区） | 计划用例 |
| AC-07.2 | 队列的一次任务完成 → 平台出现 `a2/queue/task_done`，含 `task_id` 与结果摘要 | 同上 |
| AC-07.3 | 桥接进程挂掉 → 队列照常工作（不受影响）；恢复后从「最后一条」续；无法补齐的窗口要**写明缺口** | 同上 |

### FR-08 router 接入

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-08.1 | router 订阅平台；每收到一个事件 → 发布 `a2/router/speech`，内容是现在 `speech.jsonl` 里那句话**逐字一致** | 计划用例 |
| AC-08.2 | router 每 `--interval` 发布一次 `a2/heartbeat/router`（retain=true） | 同上 |
| AC-08.3 | 平台不可达 → router 不崩、按 Q2 的决定降级（继续读队列或只记日志），持续重连 | 同上 |
| AC-08.4 | 关掉接入（开关）→ 行为与现在**完全一致**（既有 router 测试全绿） | 既有测试 |

### FR-09 watchdog 接入

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-09.1 | watchdog 订阅 `a2/heartbeat/#`；某组件心跳超阈值 → 判出 `router_missing` / `channel_missing` / `bus_missing` | 计划用例 |
| AC-09.2 | 一条告警**同时**出现在三处：平台（`a2/watchdog/alert`）、`audit.jsonl`、现有渠道事件流；三处的检查名/对象/原因一致 | 同上 |
| AC-09.3 | 同一条告警（同检查 + 同对象）在冷却窗口（默认 10 分钟）内只发一次 | 同上 |
| AC-09.4 | 平台不在时 watchdog **仍然**巡检队列与 agent，告警写文件（不能因为平台挂了就全哑） | 同上 |

### FR-10 端到端演练（这一轮的「跑起来」）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-10.1 | 一条命令起：平台 + 桥接 + router + watchdog；随后发布一条测试事件；输出里**三段都在**：平台 `/health`、订阅端收到、router 说了一句、watchdog 心跳正常 | 计划用例 / 演练脚本 |
| AC-10.2 | 演练中杀掉 router → N 分钟内平台出现 `a2/watchdog/alert`（`router_missing`），`audit.jsonl` 有对应行 | 同上 |
| AC-10.3 | 演练结束后进程全退、端口释放、临时数据清掉（可重复跑第二遍） | 同上 |

### FR-11 迁移与回退

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-11.1 | 平台是**新增**：不启用时，队列事件流、router、watchdog 的行为与今天完全一致 | 既有回归 |
| AC-11.2 | 每个接入方各有开关（`--bus <url>` / `--bus none`）；关掉后日志里说清「平台未启用」 | 计划用例 |

### FR-12 与「信息传播中心」的接口约定（Q7 确认后验收）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|

| AC-12.2 | 平台消息带 `key`（幂等键），传播中心的去重直接用它 | 待 Q7 |

## 8. 非功能需求

- **NFR-01** 只用标准库、**Python 3.6 兼容**（`sched/` 的硬规矩）；
- **NFR-02** Windows 与 POSIX 都能跑，**Windows 是硬要求**（开发机在这里）；
- **NFR-03** 空转成本：没有消息时 CPU 平均 < 1%；心跳与保活有节流；
- **NFR-04** 消息体上限默认 64 KB，超限明确报错（不静默截断）；
- **NFR-05** 端口独占、单实例（复用 `smoke_port_guard` 的判据）；
- **NFR-06** 时间一律 UTC（ISO8601，毫秒），另可在日志里带本地时间；
- **NFR-07** 日志写 `~/.tea_agent/logs/`，按天轮转 + 节流（沿用队列做法）；
- **NFR-08** 不引入第三方依赖（不做 pip 安装）；
- **NFR-09** 平台自身可被观察：心跳 + `/health` + 订阅者列表；
- **NFR-10** 背压有上界：订阅者慢不拖垮平台（FR-03.4）。

## 9. 风险

| 编号 | 风险 | 对策 |
|---|---|---|
| R1 | **平台成为新的单点**：它挂了，router/watchdog/传播中心全哑 | 回退开关（FR-11）；watchdog 看平台心跳（AC-09.1）；告警同时写文件（AC-09.4） |
| R2 | **重复投递**（重连、至少一次） | `key` 幂等（AC-02.2）+ 按 id 去重（AC-03.2） |
| R3 | **背压 / 内存**：订阅者慢，平台堆消息 | 上限 + 策略 + 计数（AC-03.4） |
| R4 | **两套事实**（队列 vs 平台） | 队列是事实源，平台只分发（§5.2）；平台不写业务状态 |
| R5 | **MQTT 路线撞 ACL / TLS** | 若选 MQTT：先改 `topic_allowed()`/`publish_allowed()`（C++）+ 准备证书；retained 不落盘要写进文档 |
| R6 | **安全**：平台被当成公网入口 | 默认只听 127.0.0.1 + token；改监听地址时警告（AC-05.3） |
| R7 | **平台长成第二个传播中心**（开始判读/派任务） | 明确不做业务（§5.2）；判读与派任务留在传播中心/队列 |
| R8 | **演练用的假服务混进生产路径** | 演练脚本与生产配置分开；默认配置里没有测试 topic |

## 10. 待确认问题（必须拍板，未答复不进入设计）

> 「建议」是分析阶段的建议，不是决定。

### Q1 协议：HTTP 还是 MQTT？

用户说「http 或 mqtt」，两者皆可。事实见 §3。**建议先 HTTP**（零 C++、本机可跑），
接口语义与 MQTT 同形，以后换传输层不动上层。

### Q2 平台与队列事件流：并存还是替换？

- (a) **并存**：队列事件流照旧，桥接把事件送到平台（平台是分发层）；
- (b) 替换：router/watchdog 只订平台，队列不再对外广播（要改队列，风险大）。

**建议**：(a)。

### Q3 桥接谁做？

- (a) 独立进程（`pump`：订阅队列 SSE → 发布到平台）；
- (b) router 自己同时订阅两处（省一个进程，但 router 又多一个职责）；
- (c) 队列直接支持「往平台发布」（改队列）。

**建议**：(a)。它挂了不影响任何一方，也最容易测。

### Q4 topic 命名（定下来就写进文档，不再改）

建议：`a2/<来源>/<种类>`，例如
`a2/queue/task`、`a2/queue/task_done`、`a2/router/speech`、`a2/watchdog/alert`、
`a2/heartbeat/router`、`a2/heartbeat/watchdog`、`a2/heartbeat/bus`。

### Q5 谁能发布、谁能订阅？

- 只有本机（token 一份）？
- 多机时（Q8）怎么认证：共享 token / 每台一把 / 复用 MQTT 账号？

### Q6 窗口与保留

- 保留多少（建议 1000 条 / 60 分钟）？
- 要不要**落盘**（重启后还能补）？不落盘要写进文档，别让人以为能补。

### Q7 平台就是「信息传播中心」的「信息中心」吗？

如果是，`propagation-center.md` 的 Q1 就此落定；传播中心的「定时取消息」= 订阅本平台，
「发布消息」= 发布到本平台。这条确认后，两篇文档要互相引用。

### Q8 多机范围

- 只本机（开发机）？
- 还是要公网可达（那就接近 MQTT 的战场：TLS、账号、zone；HTTP 路线要自己做 TLS）？

### Q9 代码落点与命名

- 平台叫 `sched/bus_server.py`？桥接叫 `sched/bus_pump.py`？
- 随包发布（`sched/` 整个目录进 zip），还是开发者自用（`tools/`）？
