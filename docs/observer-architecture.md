## 0. 先对齐事实：router 与 watchdog 已经存在

它们**不是从零开始**，2026-11-01 就落地了（仓库开发笔记里记着「M0~M5 全做完」，
`docs/router-watchdog.md` 的路线表到 M6 也都 ✅）。现在有的东西：

| 组件 | 代码 | 接口 / 落点 | 常驻方式 |
|---|---|---|---|
| **Router** | `sched/router.py`（约 350 行） | 订阅队列 `GET /api/events`；线索在队列侧（`GET /api/threads`、`POST /api/threads/{id}/spill`）；话术落在 `~/.tea_agent/router/speech.jsonl`，并以 `speech` 事件递回队列 | Linux：`scripts/a2_router.service`（systemd --user） |
| **Watchdog** | `sched/watchdog.py`（约 700 行） | 巡检队列 `GET /api/tasks`、agent `GET /api/health`、机群 `GET /api/...`；告警塞进队列事件流（`watchdog_alert`）；审计在 `~/.tea_agent/watchdog/audit.jsonl`（只追加） | Linux：`scripts/a2_watchdog.service`（systemd --user） |
| **触发器入口** | `sched/triggers.py` + 队列 | `POST /api/triggers`、`GET /api/triggers`、`GET /api/threads` | 队列的一部分 |
| **安装** | `scripts/install-units.sh` | 装 `a2 / a2_task / a2_wechat / a2_telegram / a2_fleet / a2_watchdog / a2_router` 七个单元 | `systemctl --user enable --now` |

所以「搭起来」至少有三层意思，**得先说是哪一层**（见 §9 Q1）：

| 层 | 含义 | 现在的状态 |
|---|---|---|
| **部署层** | 让它在这台机器上真的常驻跑着 | Linux 上有单元；**Windows（本机）没有**——`scripts/install-autostart.ps1` 只装 `tea_agent.exe`，队列 / router / watchdog 都没有常驻方式 |
| **能力层** | 把「观察者闭环」补完整：谁在盯谁、告警走哪条独立的路、一条消息看完今天 | 有一半，缺口见 §2.2 |
| **结构层** | 重构：两个独立脚本 → 一个「观察者服务」？还是搬进 C++ / 扩展层？ | 未动 |

本文**以能力层为主线**写（它是「观察者」这件事的实质），把部署层作为其中一条需求带上，
结构层留在 Q1/Q2 由人拍板。

## 1. 目标

| 编号 | 目标 | 怎么算做到了（可测） |
|---|---|---|
| G1 | **人是观察者**：入口有人投 → 闭环自动跑 → 人一条消息就能看到「今天发生了什么」 | 一条命令 / 一条通知里能回答：做了几件、失败几件、哪几件在等我说话 |
| G2 | **闭环看得见自己**：任何一个环节死掉都被发现，包括「看门狗自己死掉」 | 杀掉 router / watchdog / 渠道中的任意一个 → N 分钟内有一条明确的告警（「router 不在了」「watchdog 不在了」「渠道不在线」） |
| G3 | **一个声音、一份流水、一条摘要** | 话术只写一遍（router）；流水可查（speech.jsonl + audit.jsonl）；摘要一条顶一天 |
| G4 | **告警不依赖被告警的那条路** | 渠道（微信/Telegram）挂掉时，告警仍然到达人 |
| G5 | **不越权** | 默认只说不动手；动手的动作有清单、有审计；不替人对外发言 |

## 2. 现状盘点

### 2.1 已有的能力（不需要重做）

| 能力 | 在哪 | 说明 |
|---|---|---|
| 触发器统一入口 | `sched/triggers.py` | 去重 → 规则 → 模型判读 → 受理才变任务；`ignore` 优先于 `require`；判不准 = 受理 |
| 线索（thread） | 队列 + `sched/triggers.py` | 同一段对话落进同一条线索；窗口 8 步进 prompt，掉出的进 spill；router 用**一次**模型调用收拢成摘要 |
| 对外说话 | `sched/router.py` | 一个事件一句话 → `speech.jsonl` + 递回队列事件流；渠道加 `--speech` 才切过来 |
| 外面盯着 | `sched/watchdog.py` | `stalled_task`（双阈值：安静够久 **且** 进度没动）、`agent_down`、`quota_low`、`device_offline`、`drift`（问模型「跑偏了没有」，只产建议）、`plan_stuck` |
| 告警送达 | `watchdog_alert` 事件 → 队列事件流 → 渠道 | 带任务的告警推给排任务的人；不带任务的推给所有跟 bot 说过话的人 |
| 动作闸门 | 队列 `POST /api/tasks/{id}/fail`、`/api/queue/pause|resume` | 默认只告警，`--auto` 才允许 fail/retry；每次动作写审计 |

### 2.2 缺口（编号 D-xx，后面的 FR 直接引用）

| 编号 | 缺口 | 证据 | 后果 |
|---|---|---|---|
| **D-01** | **router 死了没人知道** | `sched/channel.py:971` 的 `warn_if_router_silent()` 只在**前端日志**里打一行；watchdog 的巡检项里没有 router | 切到 `--speech` 后，router 一死，**用户那边一个字都收不到**，而系统看起来一切正常 |
| **D-02** | **渠道死了没人知道** | watchdog 的告警出口就是队列事件流 → 渠道（`sched/watchdog.py:213` `escalate()`） | 渠道挂了 = 告警也挂了。告警链路和被告警对象是同一条路 |
| **D-03** | **watchdog 自己死了没人知道** | 没有心跳文件；没人查 `audit.jsonl` 的最后写入时间 | 「盯着的人」自己停了，没有人盯着他 |
| **D-04** | **没有「今天发生了什么」的一条消息** | 只有逐条的 `speech.jsonl` 与 `audit.jsonl`；机群有日报（`sched/fleet.py`），watchdog 没有 | 观察者要自己翻几十行 jsonl 才敢下结论——这仍然接近「传话筒」 |
| **D-05** | **不认识的事件 = 静默** | `sched/router.py` 的 `speak()` 对未知 `type` 返回空串；`say()` 收到空串直接返回 | 将来「信息传播中心」这类新事件源进来 → **没有人说话**，而且没有任何痕迹 |
| **D-06** | **入口积压看不见** | 没有「事件进队列 → 被 router 消费」的时延指标；队列事件流有心跳（`sched/task_server.py` 的 SSE heartbeat），但那是给订阅者保活的，不是给别人看它活没活的 | 队列堵了、router 卡了，都只能靠人感觉 |
| **D-07** | **打扰没有阈值** | router 逐事件一句，没有「必打扰 / 进摘要 / 静默」的档位 | 事件一多就变成刷屏，人不看 → 又退回传话筒 |
| **D-08** | **Windows 上没有常驻** | 只有 `scripts/install-autostart.ps1` 装 `tea_agent.exe`；队列 / router / watchdog 没有 Windows 单元 | 本机跑不成一套；开发机与部署机行为不一致 |
| **D-09** | **router 把 `reasoning` 当答案** | `sched/router.py` 的 `ask_model()`：`body.get("content") or body.get("reasoning")` | 思考型模型（deepseek-flash 等）正文为空时，**思考过程被当摘要写进线索**，下一轮 prompt 里带的是胡话。仓库里已经踩过同一个坑（`tea_a2_agent.md`「知乎发文章」一节：永远不把 reasoning 当答案） |

> D-01~D-03 是**同一个病**：闭环里没有「谁还活着」这件事的观测。D-04~D-05 是**同一个病**：
> 观察者没有「一条看完」的东西。D-09 是个已知的坑，顺手该修。

## 3. 范围

### 3.1 这次要做（能力层）

1. **自检与心跳**：每个常驻组件写心跳；有一条命令能回答「这套闭环现在健康吗」（§5 FR-01、FR-02）；
2. **独立告警出口**：告警不再只走渠道（FR-03）；
3. **一条看完的摘要**：每天（或每次巡检）一条汇总（FR-04）；
4. **router 说话的可扩展 + 不静默**：事件类型有注册表；不认识的事件要留痕（FR-05）；
5. **打扰档位**：必打扰 / 进摘要 / 静默（FR-06）；
6. **积压与时延指标**（FR-07）；
7. **部署形态**：Linux 单元（已有，修好）+ Windows 计划任务（新增）（FR-08）；
8. **watchdog 的动作清单**：默认只说不动手；「允许做什么」要可配、可审计（FR-09）。

### 3.2 这次明确不做

- 不改 agent 内核（worker 还是现在的 agent，session 还是隔离的）；
- 不把 router / watchdog 搬进 C++ 二进制（结构层另议，见 Q2）；不搬进扩展层 `a2_ext_py` 也另议；
- 不改触发器入口的现有语义（去重/规则/模型的顺序、「判不准 = 受理」）；
- 不做云端 BYOM、不做 A2A 通信、不做跨月长程记忆（沿用 `docs/router-watchdog.md` 里已写明的「明确不做的事」）；
- 不替人对外发言（自动发布到外部渠道的红线见 `docs/integrations.md` 与传播中心需求 Q4）；
- 不新增「消息中心」类功能（那是 `docs/propagation-center.md` 的事，本文只保证它接进来时**有人说话、有人盯着**）；
- 不做图形界面（观察通道用现有的通知出口 + 流水文件 + 一条命令）。

### 3.3 与「信息传播中心」的关系

```
  信息传播中心（入口层，docs/propagation-center.md）   ← 定时取消息 → 派任务 → 发布
            │ 事件进入队列（触发器入口 / 任务）
            ▼
        队列（work item）  ──► Worker（agent 的隔离 session）
            │                        │
            ▼                        ▼
        Router（串线索 + 说话）  ← 事件流
            │
            ▼
        出口（微信 / Telegram / 文件）  ← 人在这里当观察者

        Watchdog（在外面盯着上面每一个） ──► 告警（独立出口 + 审计）
```

- 本文管的是 **Router + Watchdog + 部署 + 自检**；
- 传播中心那篇管的是**入口层**；
- 两篇共用同一套「打扰档位」与「摘要」口径（传播中心 Q4/Q5 与本文 FR-04/FR-06 是同一件事，**定了要同步**）。

## 5. 功能需求与验收标准

> 每条验收标准都写成「输入 → 动作 → 期望结果」，并指明**在哪里验**。
> 「计划用例」= 实现阶段要新增/扩展的测试文件（文件名占位，以实际为准）。

### FR-01 一条命令回答「闭环健康吗」

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-01.1 | 给定 agent、队列、router、watchdog、渠道全部在线；跑自检命令；**期望**：逐项报「在/不在」，并给出最后一次心跳时间与版本 | 计划用例 `tests/smoke_observer_stack.py` |
| AC-01.2 | 给定其中一个组件的进程被杀；跑自检；**期望**：那一项报「不在」，并说明「自检时刻起已离线多久」 | 同上 |
| AC-01.3 | 给定 agent 正常但队列不通；**期望**：自检报「队列不通」，并给出最后一次成功巡检的时间 | 同上 |

### FR-02 心跳：每个常驻组件都留「我还活着」的痕迹

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-02.1 | 给定 router 在跑；**期望**：`~/.tea_agent/router/` 下有心跳文件，内容含时间戳与 pid，且不超过 N 分钟未更新（建议 N = 3×巡检间隔） | 计划用例（同上） |
| AC-02.2 | 给定 watchdog 在跑；**期望**：心跳文件同样更新 | 同上 |
| AC-02.3 | 心跳文件超过阈值没更新 → 被判为「不在」；**期望**：触发 FR-03 的告警（且告警里写明是哪个组件） | 同上 |

### FR-03 独立告警出口（不依赖渠道）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-03.1 | 配了 webhook 出口；watchdog 判出一次 `agent_down`；**期望**：webhook 收到一条（不需要渠道在线） | 计划用例 |
| AC-03.2 | 渠道（微信/Telegram）**不可用**时发生告警；**期望**：告警仍然出现在独立出口（文件/webhook） | 同上 |
| AC-03.3 | 每次告警在 `~/.tea_agent/watchdog/audit.jsonl` 留一行（含检查名、对象、动作、原因、级别）——**只追加** | 审计文件内容 |
| AC-03.4 | 同一条告警在短时间内重复发生 → 按「同一检查 + 同一对象」去重（建议冷却窗口默认 10 分钟），窗口过后再报一次 | 同上 |

### FR-04 一条看完的摘要（观察者的日报）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-04.1 | 一天里发生了 5 件事（3 成 1 败 1 等回答）；跑摘要命令；**期望**：一条消息里含这 5 件的分类计数 + 需要人说话的那几件的原文要点 + 失败原因 | 计划用例 |
| AC-04.2 | 摘要能定时自己出来（每日一条，或按巡检周期）；**期望**：到点自动出现在配置的出口 | 同上 |
| AC-04.3 | 摘要里**不含**密钥、令牌、完整 prompt 原文 | 同上（文本扫描） |
| AC-04.4 | 摘要口径与「打扰档位」（FR-06）一致：摘要里的「需要人说话」的那些**同时**会单条推给对应的人 | 同上 |

### FR-05 router 说话的可扩展，且不认识的事件不静默

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-05.1 | 队列里出现一个 router 不认识的事件类型；**期望**：`speech.jsonl` 里留下一条「不认识的事件类型：xxx」，**不是空白** | 计划用例 |
| AC-05.2 | 新增一种事件类型只需要**加一条映射**（配置或一张表），不改 router 的代码路径 | 同上 |
| AC-05.3 | router 收拢摘要时模型正文为空（思考型模型）；**期望**：**不**把 `reasoning_content` 当摘要（宁可这次不收拢），并在日志里写明原因 | 同上（修 D-09） |

### FR-06 打扰档位：必打扰 / 进摘要 / 静默

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-06.1 | 同一轮里产生 10 条普通结果、阈值 = 3；**期望**：打扰通道收到 3 条，其余 7 条只进摘要与流水 | 计划用例 |
| AC-06.2 | 失败 / 需要人拍板 / 组件掉线；**期望**：必打扰，不受阈值限制 | 同上 |
| AC-06.3 | 档位可配：某类事件可以设成「只进摘要」或「静默」 | 同上 |
| AC-06.4 | 档位配置在**一份文件**里，router 与 watchdog 与（将来的）传播中心**共用**同一份 | 同上 |

### FR-07 积压与时延

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-07.1 | 队列事件流积压（router 消费不过来）；**期望**：自检/巡检报出「事件积压 N 条，最老的一条已等 X 分钟」 | 计划用例 |
| AC-07.2 | 任务从创建到完成的时延能被统计（今日均值 / 最长 / 超过阈值的个数） | 同上 |
| AC-07.3 | 指标只读不改行为：巡检本身不因为指标异常而动手（动手要显式开） | 同上 |

### FR-08 部署形态（两台机器行为一致）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-08.1 | Linux：单元装完 `systemctl --user status a2_router a2_watchdog` 均为 running，失败能自动重启 | 装单元脚本 |
| AC-08.2 | Windows：注册计划任务（登录触发、隐藏窗口、失败重启、忽略第二实例），起停与状态可查 | `scripts/install-autostart.ps1` 同款做法 |
| AC-08.3 | 两个平台上**同一份配置**生效（配置放 tea home，不在仓库里） | 同上 |
| AC-08.4 | 没有渠道、没有队列时，router/watchdog 起来**不崩**，只是记「对方不在」 | 计划用例 |

### FR-09 看门狗的动作清单（默认只说不动手）

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-09.1 | 默认配置下，卡住的任务只被告警，**任务记录不被改** | 计划用例 |
| AC-09.2 | 显式开启后，允许的动作只有清单里的那些（候选：`fail` / `retry` / `restart 同伴`）；每次动作写审计并带原因 | 同上 |
| AC-09.3 | 清单外的动作**即使显式配置了也被拒绝**，并说明「这个动作不在允许清单里」 | 同上 |

## 6. 非功能需求

- **NFR-01** 只用标准库、**Python 3.6 兼容**（`sched/` 的硬规矩：设备上装不了 pip）；
- **NFR-02** Windows 与 POSIX 都能跑（**Windows 是硬要求**：开发机在这里，两边行为要一致）；
- **NFR-03** 不改 agent 内核；不改队列既有接口语义（**只加不改**：新增接口独立命名）；
- **NFR-04** 空转成本：没有事件时 CPU 平均 < 1%；日志按「同一句话最多每 N 秒一行」节流；
- **NFR-05** 状态与数据目录：`~/.tea_agent/router/`、`~/.tea_agent/watchdog/`（心跳、审计、状态、流水）；
- **NFR-06** 审计**只追加**，不重写历史；保留期可配（沿用队列的 `--retention-days` 思路）；
- **NFR-07** 幂等：同一个组件重复起只能有一个实例（pid 锁），避免重复说话 / 重复告警；
- **NFR-08** 一切配置集中在 tea home 的一份文件里，两个组件共用（FR-06.4）；
- **NFR-09** 可观测：每轮一行摘要日志（巡检了几项 / 告警几条 / 动作几次）；
- **NFR-10** 时区：所有时间记 UTC + 本地时间两套（`tea_a2_agent.md` 里 cron 用本机时间的坑）。

## 7. 风险

| 编号 | 风险 | 对策 |
|---|---|---|
| R1 | **告警风暴**：自检发现「渠道不在」→ 告警也要走渠道 → 反复告警 | 独立出口优先（FR-03）；去重冷却（AC-03.4）；「自己的出口也不通」只写文件 |
| R2 | **看门狗互相看 → 循环告警** | 只有一层（watchdog 看别人），watchdog 自己由「心跳缺失 + 外部巡检」判定（Q5） |
| R3 | **误杀正在跑的长任务**（既有取舍，保留） | 双阈值；默认只说；动作清单 + 审计 |
| R4 | **摘要变成噪音** | 每日一条 + 只报「需要人说话」的；同类合并 |
| R5 | **摘要/告警里泄漏密钥** | 发布前扫描（AC-04.3、AC-05.3） |
| R6 | **router 收拢摘要把思考当答案**（D-09，已存在） | FR-05.3 修掉 |
| R7 | **Windows 常驻与 Linux 行为不一致** | 同一份配置 + 同一套自检；平台差异只在「怎么起进程」 |
| R8 | **和传播中心那篇各做各的** | 两篇共用打扰档位与摘要口径（FR-06.4）；传播中心事件类型在 router 的注册表里登记（FR-05.2） |
| R9 | **范围膨胀**（顺手把队列也改了） | 明确不做（§3.2）；队列只加不改 |

## 9. 待确认问题（必须拍板，未答复不进入设计）

> **「建议」是分析阶段的建议，不是决定。**

### Q1 「搭起来」指哪一层？

- (a) **能力层**：把「观察者闭环」补完整（本文主线）；
- (b) **部署层**：在这台机器上把队列 + router + watchdog 跑成常驻；
- (c) **结构层**：重构成一个「观察者服务」，或搬进 C++ / 扩展层。

**建议**：先 (a)，(b) 顺带做（本机跑起来才验得了闭环）；(c) 另立一轮。

### Q2 结构层：这套东西住在哪？（2026-11-27：部分回答）

- 已定：router/watchdog **基于消息平台运行**（Python 侧独立进程，由平台驱动），见 `message-platform.md`；
- 仍待定：两者是否合并成一个「观察者服务」进程；要不要搬进 C++ / 扩展层（本文建议不搬）。

原选项：

- 继续 Python 侧独立进程（现状）；
- 合并成一个「观察者服务」进程（router + watchdog 一个进程两份职责）；
- 搬进 C++（agent 内核）；
- 搬进扩展层 `sched/a2_ext_py/toolkit/`（模型可调用的工具）。

**建议**：维持 Python 侧独立进程。理由与既有取舍一致：**它要是跑在 agent 里，一个卡死的 worker 就能把它一起关掉**；而且策略不该进二进制。

### Q3 告警的第二条路走哪？（独立出口选哪个）

webhook / 直发 Telegram / 直发微信 / 只写文件 + 本地弹窗 / 机器学习其它？

**建议**：默认「只写文件（必做，不依赖任何网络）」+ 可选 webhook；聊天渠道仍作为主出口但**不再是唯一出口**。

### Q4 摘要的形态与频率

- 每天一条？每轮巡检一条？还是「有需要人说话的事才发」？
- 摘要发到哪（跟告警同一个出口？还是单独的）？
- 摘要里要不要带原文要点（涉及密钥与隐私）？

### Q5 谁看 watchdog？

- watchdog 看 router + 渠道 + 队列 + agent（本文 FR-02）；
- **watchdog 自己**由谁看？选项：a) 队列定期查 `audit.jsonl` 的最后写入时间；b) 另一个极简的外部进程；c) 靠路由器的自检（但 router 也可能死）；d) 靠系统级监控（systemd / 计划任务的心跳重启 + 邮件）。

**建议**：a) + d)（队列做「谁都不在」的兜底告警写进文件），c) 不够（两个都可能死）。

### Q6 watchdog 允许哪些动作？

默认「只说不动手」保留。要不要允许：把卡死的任务判死（已有）、重试（已有）、**重启死掉的同伴**（router / 渠道 / 队列）？

**建议**：允许「重启同伴」但必须显式开、每次写审计；「判死任务」继续要求 `--auto`。

### Q7 与信息传播中心的先后？

先做观察者层（本文），还是先把入口做出来（传播中心那篇）？两篇的「打扰档位」与「摘要」要不要**合并成一份共用配置**（本文 FR-06.4 建议合并）？

### Q8 本机（Windows）要不要常驻？

本机是开发机（`tea_a2_agent.md`：本机只做实现 + 本地自测，发版与正式测试在另一台机器）。
- 要不要在本机装常驻（计划任务），还是只提供「一键起一套」的脚本供手动验证？

**建议**：提供一键脚本 + 可选注册；不默认常驻。

### Q9 摘要与告警的保留期？

`audit.jsonl` / `speech.jsonl` 留多久？沿用队列的 `--retention-days` 默认值？
