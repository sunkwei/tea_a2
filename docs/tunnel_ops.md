# 隧道现场操作指引：两台机器各跑两条命令

> 给客户现场的运维同事 / 我们的实施同事照着做。
> 目的：在装任何东西之前，先确认**这两台机器之间能不能直接打洞**。
> 全程约 5 分钟，不需要装任何软件、不需要 root。

---

## 一、要确认什么

一句话：**外网能不能直接连到内网那台设备上的 tea_a2**（中间不经过任何中转服务器）。

> ⚠️ **先看已有的实测结果**（2026-11-09，zonekey 192.168.12.12 / 公网 36.112.70.164，
> 网络出口是家用路由器 + 运营商宽带）：
>
> ```
> [probe] NAT 判定：symmetric
> [probe]   依据：同一个 IP(46.225.95.169) 换个端口，映射端口就变（27889, 46693）
> ```
>
> 打了**三种**组合，**全部失败**（两边都是 0 收 0 发）：
>
> | 组合 | 结果 |
> | --- | --- |
> | 内网当 agent、外网当 client，单向打 | 23 个包，0 回包 |
> | 外网当 agent、内网当 client，单向打 | 25 个包，0 回包 |
> | **两边同时主动打**（真实 ICE 的做法） | 各 100 个包，0 回包 |
>
> **家用宽带 + 家用路由器 → 对外是对称 NAT（运营商侧大概率还有一层 CGNAT，
> 而且常常直接丢弃外来的 UDP）→ 教科书式打洞不通。**
>
> **这不影响交付**：隧道的设计里**中继（TURN）是主路径，直连只是优化**。
> 这一页的实测是为了知道「能直连还是必须中继」，不是为了卡住项目。

---

## 二、怎么跑（协议和真实 ICE 一样：两边都知道对方地址，同时打洞）

### 第 1 步：两台机器各拿一个 token

```bash
# 内网那台（客户设备）
python3 nat_probe.py probe
# 外网那台（运维同事的机器）
python3 nat_probe.py probe
```

各自输出：

```
[probe] 用的 STUN 服务器：stun.l.google.com:19302
[probe] NAT 判定：symmetric
[probe]   依据：同一个 IP(46.225.95.169) 换个端口，映射端口就变（27889, 46693）
[probe]   stun.l.google.com:19302      ip=74.125.250.129   端口 19302 -> 反射 36.112.70.164:32940
...
  ---- 我的 token（抄给对方）----
  36.112.70.164:32940:eddfa8
  --------------------------------
```

⚠️ **看两边的「用的 STUN 服务器」是不是同一个**——两边必须经同一个服务器看地址，
否则对称 NAT 两侧的端口没有可比性。（默认列表顺序一样，通常一致；不一致就加
`--stun <host:port>` 指定同一个。）

### 第 2 步：把两边的 token 互抄给对方

A 拿到 B 的 token，B 拿到 A 的 token。

### 第 3 步：两边**同时**跑

```bash
python3 nat_probe.py punch --mine <自己的token> --peer <对方的token>
```

两边都要**同时**开始（这是关键：NAT 的入站放行规则要靠「双方都发过包」才打开）。

```
[punch] 我 39.65.223.83:59933 -> 打 36.112.70.164:25272（40 秒，每秒 5 个包）
[punch] 发了 100 个包，收到 100 个回包，延迟 23 ms
[punch] 结论：P2P 打洞成立（双向都通）。
```

---

## 三、验收标准

| 输出 | 结论 |
| --- | --- |
| 两边都是 **「P2P 打洞成立（双向都通）」** | ✅ 这条网络能直连（延迟最低、流量不过第三方） |
| 任何一边 **「打不通」** | ⚠️ 走中继即可，**不影响使用**。见下面第四节 |

顺手记下这几个数，交付时有用：
**NAT 判定**（cone / address-dep / symmetric）、**反射地址**、**往返延迟**（毫秒）。

---

## 四、打不通怎么办

按这个顺序排查（从最常见到最罕见）：

| 现象 | 大概率原因 | 怎么办 |
| --- | --- | --- |
| `[probe] 警告：所有 STUN 服务器都没回` | 这台机器**出不了 UDP**，或者 UDP 被防火墙挡了 | 换个网络环境试；问客户 IT 放行出站 UDP（到我们 broker 的 3478 和 443） |
| `NAT 判定：symmetric` | 前面还有一层运营商 NAT（CGNAT，100.64.x.x） | 打洞大概率失败 → 隧道靠 **TURN 中继**兜底；这在移动/部分宽带上很常见 |
| `NAT 判定：address-dep` | 映射端口随目标地址变（换目标 IP 就换端口） | **不一定**打不通（看过滤规则）→ 先按正常流程实测；不通就靠 TURN |
| STUN 有回应，但两边互相打不通 | ① 运营商 CGNAT 直接丢弃外来 UDP；② 家用路由开了「AP 隔离」；③ UDP 端口回收太快 | 换一台路由器 / 有线试；把 UDP 超时调大；**最终都靠 TURN** |
| 偶尔通、偶尔不通 | 映射端口在变（准对称 NAT） | 走中继兜底；或改用 TURN |

**这些都不是「做不了」**：TURN 中继本来就是设计的一部分
（ICE 的候选里本来就有 relay 候选，打不通时 ICE 自己选中继，运维同事无感）。
而且走 TURN 时 **broker 转发的是 DTLS 密文**，看不到会话内容。

## 五、跑这个脚本需要什么

- **Python 3.6+**（`python3 --version` 看一下就行）。设备上的 a2 是单二进制、没有 Python，
  那就在**同网段另一台**有 Python 的机器上跑 probe——只要它和设备在同一个 NAT 后面就行，
  测的是**网络路径**，不是那台机器。
- 不需要 root、不需要编译、不装任何东西。
- 脚本：`tools/tunnel_probe/nat_probe.py`（随隧道侧载一起发给现场，或者直接贴这段代码过去）。
- 默认会问 5 个公共 STUN：`stun.l.google.com` / `stun.cloudflare.com` /
  `stun.nextcloud.com:3478` 与 `:443`（**同一个 IP 的两个端口**，用来测 symmetric）/
  `stun.miwifi.com`（国内那个，省得出不去 google）。也可以自己指定：
  `--stun <host:port>`（可重复，**两边要一样**）。

---

## 六、跑完之后

把两边的输出（尤其是那三行）发回我们，就能确定：

- 隧道走直连还是走中继；
- 需不需要开 TURN；
- 现场实施时 broker 的 STUN 端口要放行哪几个。
