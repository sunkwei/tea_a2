## 1. 为什么做这件事（背景）

随着 tea_a2 的进展，人与系统的关系变成了「**传话筒**」：

- 外面（设备、运维、另一台机器、另一个系统）有了动静，**得由人把它搬进 tea_a2**
  （贴进聊天窗、投 webhook、在终端敲一条命令）；
- tea_a2 干完了，**又得由人把结果搬出去**（贴回群里、发微信、告诉那台设备）；
- 人在这条链上唯一做的事就是**转发**。人不在，系统就停着；人一直在，成本就是人一直盯着。

要做的是把这条链自己接上：**定时从「信息中心」取消息 → 执行任务 → 发布消息**。
人从「传话筒」变成「**观察者**」——平时只看，需要拍板的时候才被叫醒。

### 1.1 「传话筒 → 观察者」的可测判据

| 现在的样子 | 要的样子 |
|---|---|
| 消息进来要人转述一遍 | 消息自己进来（人一句都不说） |
| 结果出去要人复制粘贴 | 结果自己出去 |
| 人要盯着才安心 | 人看一份流水就安心 |
| 人离开就停摆 | 人离开照跑，异常才叫人 |
| 一周里人手工转发 N 次 | 一周里人手工转发 0 次（除了异常与需要拍板的事） |

### 1.2 仓库现状（事实陈述，不是判断）

**已经有、可以复用的零件：**

| 零件 | 位置 | 它已经能干什么 |
|---|---|---|
| 触发器入口 | `sched/triggers.py` | 统一事件入口：去重 → 规则 → 模型判读 → 受理才变任务；`POST /api/triggers`、`GET /api/threads` |
| 定时任务 | `sched/schedules.py` + `sched/cron.py` | 五段 cron（最小粒度一分钟）；`POST /api/schedules`；上一次没做完下一次不排；错过的分钟合并成一次 |
| 任务队列 | `sched/task_server.py` | 排队、执行、事件流 `GET /api/events`、项目钥匙、幂等键、交互挂起 |
| 出口（通知） | `sched/channel.py` | 微信 / Telegram 通知；`notify_event` / `deliver_speech` |
| 线索与说话 | `sched/router.py` | 把多次会话串成一条线索，并给每个事件说一句话 |
| 看门狗 | `sched/watchdog.py` | 在外面盯着卡住的任务、agent 健康、额度 |
| watcher 的成熟形状 | `sched/mail_watch.py` + `docs/integrations.md` | 「别人那边发生了事」：取 → 判 → 动 → 留痕 → 通知 → 交办 |
| MQTT | `src/mqtt_server.cpp` / `src/mqtt_client.cpp` / `docs/mqtt_control.md` | broker + 设备注册（retained）+ 隧道召唤；设备按 operator 分区（zone） |

**这条需求直接撞到的三个已知缺口（`docs/integrations.md` 文末自己也列了）：**

1. 队列没有「只通知、不干活」的记录类型 → watcher 的通知绕过队列事件流，队列网页里看不到；
2. 没有 watcher 基类 → 第二个源落地时容易各写一套（`run_round` / `State` / `Lock` / `Notifier` 该抽出来）；
3. agent 侧没有 `callback_url` → 「任务做完」只能靠机器人前端或轮询知道。

**还有一个与本需求直接相关的限制（要在 Q1 拍板）：**

MQTT broker 的 topic 白名单目前只有 `mt_register/#` 与 `mt_control/...`，
operator 账号只能发 `mt_control/+/cmd`（`src/mqtt_server.cpp` 的 `topic_allowed` / `publish_allowed`）。
**broker 里现在没有「消息板」这一族 topic。** 如果「信息中心」就是 MQTT 上的消息板，
那需要另立一条需求去扩 broker 的 topic 族与权限（那是 C++ 侧的改动，不在本文范围内）。

## 2. 目标

| 编号 | 目标 | 怎么算做到了（可测） |
|---|---|---|
| G1 | **闭环自动化**：一条消息进入信息中心后，人不参与也能走完「取 → 执行 → 发布」 | 造一条消息放进消息源，除启动中心外无人操作；一轮之后出口收到结果 |
| G2 | **人变观察者**：默认只有摘要与异常打扰人 | 一天 10 条普通消息 → 打扰次数 ≤ 配置阈值（默认建议 3），其余进摘要 |
| G3 | **可追溯**：每条消息都有去向 | 一条命令能列出「每条消息：何时进来 / 判成什么 / 派了哪个任务 / 发到哪 / 成没成」 |
| G4 | **不重复干活** | 同一条消息重复到达只做一次；重启后不重做已完成的 |
| G5 | **不越权**：能触发的动作有边界，发布出去的内容不泄漏密钥 | 越界的命令没执行；发布文本命中密钥则被拦下 |

## 3. 范围

### 3.1 这次要做（暂定形态，取决于第 9 章）

- 一个**常驻的传播中心**（Python 侧进程，与 `sched/` 同族）：定时轮询 → 取消息 → 判读 → 派任务 → 发布结果 → 留痕；
- 一份配置：消息源、轮询频率、出口、打扰阈值、预算上限、暂停开关；
- 一条「观察」通道：摘要 + 异常推送 + 可查的流水（CLI）。

### 3.2 这次明确不做

- 不改 C++ 内核（除非 Q1 选定 MQTT 消息板——那要另立需求扩 broker 的 topic 与权限）；
- 不新造第二套队列 / 触发器 / 出口（复用 §1.2 表里的零件；复用范围见 Q11）；
- 不替人回邮件、不替人对外发言（既有红线，见 §7 与 Q4）；
- 不做多租户、不做计费、不做权限继承；
- 不做消息的密级与脱敏体系（只做「不把密钥发出去」这一条底线）；
- 不回放历史消息（只处理新进来的）；
- 不改 provider / 模型选择逻辑，不新增模型能力；
- 不做「消息中心」自己的图形界面（观察通道先用现有的通知出口 + 流水文件）。

| 词 | 意思 |
|---|---|

| **出口** | 结果发出去的地方（待 Q4 拍板）。 |
| **观察者** | 人在这套系统里的新角色：不转发，只在需要时看 / 拍板。 |

## 6. 功能需求与验收标准

> 验收标准都写成「输入 → 动作 → 期望结果」，每条都指明**在哪里验**。
> 「计划中的用例」指实现阶段要新增的测试文件（文件名只是占位，实现时以实际为准）。

### FR-01 定时取消息

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-01.1 | 给定消息源里有 3 条未处理消息、中心配置 `interval=30s`；启动中心并等一轮；**期望**：3 条都被取到，状态文件里的游标落在这 3 条之后 | 计划用例 `tests/smoke_propagation_center.py` |
| AC-01.2 | 给定消息源里没有新消息；跑一轮；**期望**：不派任何任务、日志写「无新消息」、**不消耗任何模型调用** | 同上 |
| AC-01.3 | 给定进程在取到消息、派任务之前被 kill；重启；**期望**：不重复派已完成的活儿；被中断的那条按 §7.4 处理 | 同上 |

### FR-02 去重：同一件事只做一次

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-02.1 | 同一条消息（同一 `dedup_key`）连投两次；**期望**：只产生一个任务；第二条记录指向同一个任务 id | 同上 |
| AC-02.2 | 两条内容相同但 `dedup_key` 不同的消息；**期望**：当作两件事，各派一个任务 | 同上 |

### FR-03 判读：这件事要不要做

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-03.1 | 消息命中「忽略」规则；**期望**：不派任务，记录判成 `ignore` 并写明命中了哪条规则 | 同上 |
| AC-03.2 | 消息命中「受理」规则；**期望**：派任务 | 同上 |
| AC-03.3 | 规则没定音 → 问模型一次；模型答不上来 / 超时 / 返回的不是 JSON；**期望**：按「受理」处理（宁可多派一个可取消的任务，也不让一条真活儿悄悄消失） | 同上 |
| AC-03.4 | 规则与提示词写在配置里；改配置后**下一轮就生效**，不用重启 | 同上 |

### FR-04 派任务、真做

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-04.1 | 受理的消息 → 队列里出现一个任务，`meta` 里带来源、消息 id、消息摘要 | `GET /api/tasks`（队列） |
| AC-04.2 | 任务跑完 → 队列记录里的 `result` 是**完整答案**（不是截断的 300 字） | `GET /api/tasks/{id}` |
| AC-04.3 | 任务失败 → 记录失败原因，并按「必打扰」规则通知（见 FR-06） | 同上 |

### FR-05 发布结果

| 编号 | 验收标准 | 在哪验 |
|---|---|---|
| AC-05.1 | 任务完成 → 配置的出口收到一条消息，内容至少含：原始消息摘要、结果、任务 id、时间 | 出口的假服务 / `channel.py` 的通知 |

| AC-05.3 | 发布文本里出现 provider.yaml 的 key / 令牌 → **拒绝发布**并记录（AC：文件真的没发出去） | 同上 |
| AC-05.4 | 发布的正文里**不含**内部 id 之外的敏感路径（待 Q4/Q8 定边界） | —— 待确认后补 |

## 7. 非功能需求

### 7.1 兼容性

- **NFR-01** 只用标准库、**Python 3.6 兼容**（`sched/` 的硬规矩：设备上装不了 pip）；
- **NFR-02** Windows（本机 SUNKW-X1）与 POSIX 都能跑；
- **NFR-03** 不改 C++ 内核（Q1 若是 MQTT 消息板则另议）。

### 7.2 安全与边界

- **NFR-04** 不代替人对外发言：默认出口是**内部**通道；对外发布必须显式配置（Q4 拍板），并沿用 watcher 的红线「发送类的动作留给人」；
- **NFR-05** 发布内容不泄漏密钥（AC-05.3）；
- **NFR-06** 外部消息当 prompt 跑工具 = prompt injection 风险：能触发的动作要有清单，超出清单的走「先判后做」或人工确认（Q8）。

### 7.3 可靠性

- **NFR-07** 进程崩溃 / 重启后状态一致：已完成的**不重做**，游标不丢（AC-01.3）；
- **NFR-08** 单实例（AC-08.1），避免同一消息被执行两次；
- **NFR-09** 投递失败有重试与兜底（AC-05.2）。

### 7.4 中断与恢复的取舍（**假设 A1，待确认**）

沿用队列已有的规矩：**一轮被切断的活儿可能已经做了一半，没人叫你别重跑，那就别重跑。**
所以：中断的那条消息默认**不自动重做**，标记成「待人工确认」，在流水里写明。

### 7.5 性能与成本

- **NFR-10** 空转成本：没有新消息时，CPU 占用平均 < 1%；日志按「同一句话最多每 N 秒一行」节流（沿用队列做法）；
- **NFR-11** 只在「有新消息」时才可能调模型；判读模型调用次数每天有上限（Q10）；
- **NFR-12** 不复用队列的全量列表接口做轮询（历史上「一文件一记录 + 全目录扫描」是平方级的坑，见 `tea_a2_agent.md`）。

### 7.6 可观测

- **NFR-13** 每轮一行摘要日志（取到几条 / 派了几个 / 发布了几条 / 跳过了几条 / 花了多少次模型调用）；
- **NFR-14** 流水文件按天追加（AC-07.2）；
- **NFR-15** 状态目录 `~/.tea_agent/propagation/`（配置、游标、流水、锁）；日志 `~/.tea_agent/logs/`。

## 8. 风险

| 编号 | 风险 | 后果 | 对策（待 Q 确认后定稿） |
|---|---|---|---|
| R1 | 外部消息被当 prompt 直接跑工具 | 外部内容可以指使模型做事（注入） | 动作清单 + 围栏 + 必要时「先判后做」（Q8） |
| R2 | 自动发布越界，替人对外发言 | 群里发出不该发的内容；这是 watcher 明写的红线 | 默认内部出口；对外发布要显式配置 + 白名单（Q4） |
| R3 | 重复投递（MQTT QoS1 / retained / webhook 重试） | 同一件事做两遍，烧钱 | `dedup_key`（AC-02.1） |
| R4 | 轮询空转与模型调用成本 | 一台机器 24 小时空转 | 间隔 + 每轮上限 + 每日预算 + 无消息不调模型（Q3、Q10） |
| R5 | broker 的 topic ACL 挡住「消息板」 | 选了 MQTT 消息板却发不进去 | Q1 拍板；若选 MQTT，需另立需求扩 broker |
| R6 | 队列长了就慢（历史平方级坑） | 轮询把队列拖慢 | 不走全量列表接口；用过滤/事件接口（NFR-12） |
| R7 | 时区与时钟 | cron 用**本机时间**；机器时区不对 → 触发时间不对 | 明确时区并在流水里记 UTC + 本地时间 |
| R8 | 密钥出现在发布内容里 | 凭据外泄 | AC-05.3 拦下 |
| R9 | 中心自己坏了却没人知道 | 事情静悄悄地不发生 | 「长时间没跑过一轮」必打扰（阈值待 Q5） |
| R10 | 观察者变噪音（每条都推） | 人不看 → 又变回传话筒 | 阈值 + 摘要 + 每日一条（Q5） |

## 9. 待确认问题（必须拍板，未答复不进入实现）

> 每条都给了选项与影响。**「建议」是分析阶段的建议，不是决定**——拍板权在人。

### Q1（最关键）「信息中心」到底是哪一个？

| 选项 | 说明 | 影响 |
|---|---|---|
| a) **MQTT broker**（现有的 `a2_broker`） | 别人往 broker 的某个 topic 发消息，中心订阅它 | broker 现在**没有消息板 topic 族**，要改 C++（另立需求）；重投/retained 要处理 |
| b) **中心自带的收件箱** | 中心自己开一个 HTTP 入口（或文件/DB 目录），别人往里 POST / 写文件 | 全在 Python 侧，不动 C++；认证与幂等要自己定 |
| c) **多源合一** | MQTT + 邮件 + 聊天/webhook 各接一个源，统一进中心 | 工作量最大；但正是 `docs/integrations.md` 里 watcher 的终局形状 |
| d) **现有的触发器入口就是信息中心** | 不再有独立消息源：`sched/triggers.py` 的 `/api/triggers` 收消息，中心订阅队列事件流 | 复用最多；但「定时取消息」变成「订阅」 |

**建议**：先用 (b) 或 (d) 落地一条最小闭环，把 (a) 的 topic 族留成独立需求——但这取决于你实际想接的是不是 MQTT 上的东西。

### Q2 消息长什么样？「执行任务」到底执行什么？

- a) 消息正文**直接当 prompt** 交给 agent；
- b) 消息带结构化字段（动作名 + 参数），映射到**固定配方**（可控、可审计，但要先定义动作集）；
- c) 消息只说明「发生了什么事」，由中心按来源自己决定要做什么。

**建议**：若消息来自外部系统，(b) 更可控；但需要你先列出「要做的那些事」。

### Q3 「定时」的语义与频率

- 固定间隔（每 N 秒）还是 cron（每天几点）？两者都要吗？
- 默认频率是多少？
- 错过了的时间点怎么办？（队列现有规矩：错过的分钟**合并成一次**，不补跑一串）

### Q4 发布到哪里？允许发到哪里？

- 出口候选：回到消息源（reply-to）/ 另一个 topic / 微信 / Telegram / webhook / 写文件 / 只进流水；
- **能不能对外发布**（发到群里、发给别人）？这是 watcher 明写的红线「发送类的动作留给人」——需要你明确授权边界。
- 一次发到多个出口吗？

### Q5 观察者模式：什么必打扰、什么只进摘要？

- 必打扰：失败 / 异常 / 长时间没跑 / 需要人拍板？
- 只进摘要：普通成功结果？
- 完全静默：哪些？
- 要不要「每日一条汇总」？汇总里包含什么？
- 阈值默认多少（建议 3/轮）？

### Q6 谁可以往信息中心投消息？认证怎么算？

- MQTT 账号？HTTP token？还是只有本机可信来源？
- 谁能投「高权限动作」的消息（区分普通消息与指令）？

### Q7 幂等与顺序

- 同一消息重复投递：按 `dedup_key` 去重（默认建议沿用 triggers 的规则）——确认？
- 消息之间有先后依赖吗（后一条要等前一条做完）？
- 串行处理还是并发？并发上限？

### Q8 执行边界与失败处理

- 消息能触发的动作清单（只读巡检？允许改文件？允许跑命令？）；
- 失败重试几次？失败后谁兜底（自动重试 / 记下来等人看 / 直接告警）；
- 遇到「需要人拍板」的消息怎么办（挂起等回答，还是标出来等人来查）？

### Q9 部署形态与运行位置

- 常驻进程（systemd / Windows 计划任务 / 托盘 appstub）？跑在哪台机器（本机开发机 / 公网 broker 那台 / 每台设备）？
- 与任务队列同机吗？中心能不能自己拉起队列？

### Q10 成本上限

- 每轮最多取几条？每天最多多少次模型调用？超限了是停一天还是只停本轮？
- 判读用哪个模型（便宜的 flash 还是贵的）？

### Q11 复用现有零件还是另起一套？

现有可复用：触发器入口（去重/规则/模型判读）、队列（执行）、cron（定时）、router（线索）、watchdog（盯着）、channel（出口）、mail_watch 的 watcher 形状。

**建议**：全部复用，只新增「取消息 + 编排 + 留痕 + 摘要」这一层；顺手把 `docs/integrations.md` 里列的三个缺口补掉（队列的 notice 记录类型、watcher 基类、`callback_url`）。需要你点头。

### Q12 名字与落位

- 这个东西叫什么？（内部叫「传播中心」？对外叫什么？）
- 放 `sched/`（随包发布）还是 `tools/`（开发者自用）？
