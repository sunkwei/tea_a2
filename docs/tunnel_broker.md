# broker 机器（VPS）准备清单

> 隧道的中枢：**STUN 服务器 + 信令服务器 + TURN 中继**，一个进程。
> 它是整个方案里**唯一必须站在公网上的东西**。
> 这页给运维/采购照着开机器、开口子、验收。

---

## 一、为什么要一台 VPS

打洞实测失败了（家用宽带 + 家用路由器这条网络，三种组合全灭），
所以**中继是主路径**。中继要有地方跑，而它必须：

- 有**稳定的公网 IP**（不能是 NAT 后面）；
- 能被两边主动 UDP 到（内网侧载要能 UDP 到它）；
- 能被两边 TCP 443 到（信令走 HTTPS）。

自己家的机器、办公室的机器都可能没有公网 IP 或者没有固定 IP，
**一台最便宜的轻量 VPS 就是最省事的答案**。

---

## 二、机器配置（够用就行）

| 项 | 建议 | 说明 |
| --- | --- | --- |
| CPU / 内存 | **1 核 / 1 GB** 起 | broker 平时闲着，中继转发是 IO 不是 CPU |
| 硬盘 | 20 GB | 只放一个二进制 + 日志 |
| 带宽 | **按量，流量是真正的成本** | 见 §五 |
| 操作系统 | Ubuntu 22.04 / Debian 12 | 和 a2 的构建线一致 |
| **公网 IPv4** | 必须 | 静态地址，别用 NAT 机器 |
| **公网 IPv6** | 建议 | 有的话两边可能直接走 IPv6，**连打洞都不用** |

### 选哪里

| 地区 | 延迟（到国内客户） | 备案 | 建议 |
| --- | --- | --- | --- |
| **香港** | 30–60 ms | 不需要 | ✅ **推荐**：便宜、免备案、开端口自由 |
| 新加坡 / 日本 | 60–120 ms | 不需要 | 备选 |
| 中国大陆 | 10–30 ms | **需要 ICP 备案** | 客户已有备案/已有大陆机器才考虑 |

> **备案这条要提前说清楚**：大陆服务器用域名提供 443 服务，普遍需要 ICP 备案，
> 而且备案要几周。**香港/新加坡的机器没这个问题**，省下的时间比那 20 ms 值钱。

### 大概多少钱

- 轻量应用服务器（1 核 1 GB）：**约 ¥30–60/月**（腾讯云/阿里云香港）。
- **带宽另算**：中继模式下所有会话流量都过这台机器（见 §五）。

## 三、要开哪些端口（照抄）

| 端口 | 协议 | 用途 | 必须？ |
| --- | --- | --- | --- |
| **443** | TCP | **信令**（HTTPS，交换 SDP/ICE 候选、令牌校验） | ✅ 必须 |
| **3478** | UDP | **STUN**（ICE 的第一步：问「你看到我是谁」） | ✅ 必须 |
| **443** | UDP | STUN 的备用端口 | 建议（有些网络只放行 443） |
| **5349** | TCP | **TURN over TLS**（UDP 全被封时的救命通道） | ✅ 强烈建议 |
| 49160–49260 | UDP | **TURN 中继端口池**（relay_port_range） | ✅ 必须（开 TURN 就要） |

说明：

- **3478/443-UDP 是 STUN**：UDP 出站被限的公司网不少，但出站 UDP 到 broker 通常是通的
  （不然连 STUN 都问不到，ICE 连第一步都走不了）。
- **5349/TCP 是 TURN over TLS**：**这是「UDP 全封也能用」的保险**。
  隧道会退化成一条普通的 TLS over TCP 连接，延迟高一点，但一定能通。
- **中继端口池**给 100 个足够了（每个并发会话占 1~2 个）。开得少一点，防火墙口子就少一点。

### 防火墙怎么开

```bash
# 腾讯云/阿里云的安全组 + 系统防火墙都要放行
ufw allow 443/tcp
ufw allow 3478/udp
ufw allow 443/udp
ufw allow 5349/tcp
ufw allow 49160:49260/udp
```

⚠️ **云厂商的安全组和机器上的 ufw/firewalld 是两层**，只开一层不通。

## 四、装什么

broker 是**一个二进制**（和 a2 同一个仓构建）：

```
a2_broker            # STUN + 信令 + TURN，一个进程
```

- 不需要 Python、不需要 Docker、不需要数据库；
- 配置就一个文件：`~/.tea_agent/broker.yaml`（设备令牌表、端口、日志级别）；
- systemd 单元：`a2_broker.service`，`Restart=always`；
- 日志：journald 或 `/var/log/a2_broker.log`（轮转）。

**安全底线**：

- broker **只监听上面那几个端口**，不开放 shell/管理端口；
- 每个设备一个令牌（强随机、逐设备、可吊销），存在配置里（0600）；
- broker **不记录会话内容**（走 TURN 时它转发的是 DTLS 密文，看不到 token/prompt/文件）；
  但**连接建立/断开/每次请求**要落日志（审计）。

## 五、带宽是真正的成本（提前跟人说清）

中继模式下，**内网 a2 ↔ 外网运维 的所有流量都过这台 VPS**：

- a2 的回答、SSE 流、文件、截图、模型请求……全都要从客户上行→VPS→外网，
  **下行也是**（VPS→外网那一段也要计流量）；
- 好处：流量是 **DTLS 密文**，broker 看不到内容；
- 坏处：**按量计费的 VPS 上，这笔钱是实打实的**。

所以：

- 流量小的场景（大部分：只是运维远程问几句、看看状态）→ 一个月几十 MB，**几乎不花钱**；
- 经常传文件/看视频 → 流量会明显上去，**要么加带宽包，要么让客户用自己的 VPS**。

**另一个省钱的思路**：broker 放到**客户自己的公网机器**上（他们常有），
流量不出他们的网络，也没有我们的带宽账单。协议一样，只是换个部署位置。

## 六、验收清单（机器开好之后）

```bash
# 1) 端口通不通（从外网测）
nc -u -z -w2 <vps-ip> 3478          # STUN
nc -u -z -w2 <vps-ip> 443           # STUN 备用端口
nc -z -w2 <vps-ip> 443              # 信令
nc -z -w2 <vps-ip> 5349             # TURN over TLS

# 2) STUN 是不是真的在应答（用我们自己的探针，当 STUN 服务器用）
python3 tools/tunnel_probe/nat_probe.py probe --stun <vps-ip>:3478

# 3) broker 健康检查
curl -s https://<vps-ip>:443/health
```

第 2 步的输出里，「反射地址」应该就是那台 VPS 看到的你的公网地址；
映射端口规律也会告诉我们**从客户那条网络看出去**是不是对称 NAT。

## 七、接下来

VPS 开好之后，顺序是：

1. 先把 **broker 骨架**立起来（libjuice 的 server 模式：STUN + TURN，一个进程）；
2. 用 `nat_probe.py --stun <vps>:3478` 和 `--stun <vps>:3478 --stun <vps>:443`
   在**真客户网络**上再测一次 STUN 行为（这次是「我们自己控制的 STUN」，结果更可预期）；
3. 再写两个侧载（`a2_tunnel --agent` / `--client`），跑通 **帧化 HTTP over TURN**；
4. 最后接进 `peers:`（a2 侧零改动）。
